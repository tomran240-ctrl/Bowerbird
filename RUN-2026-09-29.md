## 4. The hours-run promotion — why week 2026-09-14

This is the one code path in the payroll feed that has never run:
`payroll_hours_run_extras`, `payroll_hours_line_each` and `_mins()`, writing into
tables whose `*_hours` columns are `GENERATED ALWAYS AS ... STORED`. Both
`payroll.hours_run` and `payroll.hours_line` are empty.

Two weeks are staged and either could be promoted. **Week 2026-09-14 is the
better test**, because it is the week where the arithmetic disagrees with itself
in hours:

```
60.25 + (-2.68) + 0.12 = 57.69      hours, rounded to 2 dp
3615  + (-161)  + 7    = 3461       minutes, exact  = 57.68 h
```

That is the case the whole minutes-are-canonical decision was made for. If
`_mins()` truncated instead of rounding, it would reconstruct
`3615 - 160 + 7 = 3462` against a stored clocked figure of 3461 and the table
CHECK would fire. So promoting this week exercises the conversion at the one
point where it could be wrong.

### The round trip was verified against the ledger first

Reading the ledger's integer minutes, converting to hours the way the producer
does (`round(m/60, 2)`), then back the way the promoter does (`round(h*60)`):

| | rostered | adj_a | adj_b | clocked |
|---|---|---|---|---|
| ledger minutes | 3615 | −161 | 7 | 3461 |
| after round trip | 3615 | −161 | 7 | 3461 |

Identical, and `3615 + (−161) + 7 = 3461` holds. Every one of the seven lines
round-trips exactly as well:

| Line | rostered | adj_a | adj_b | clocked |
|---|---|---|---|---|
| Linda Storbeck | 1680 | 20 | 4 | 1704 |
| Mansi Gajera | 420 | 7 | 2 | 429 |
| Naomi Benfield | 390 | −16 | 0 | 374 |
| Ashley Brice | 375 | 0 | 1 | 376 |
| Tanisha Purushothaman | 360 | −197 | 0 | 163 |
| Meera Thomas | 210 | 17 | 0 | 227 |
| Mia Todd | 180 | 8 | 0 | 188 |

So the CHECK should pass. If it does not, the fault is in `_mins()` or in the
promoter's column mapping, not in the data — worth saying in advance, because
that is the difference between a five-minute fix and an afternoon.

Tanisha Purushothaman's −197 minutes against 360 rostered is presumably the
run's one exception action. It is an attendance variance and takes no part in
pay, which is the point of the rostered/clocked split.

### After promotion, the checks worth running

```sql
-- the stored minutes must match the ledger exactly
SELECT r.pay_week_start, r.rostered_minutes, r.adj_a_minutes,
       r.adj_b_minutes, r.clocked_minutes,
       r.rostered_minutes + r.adj_a_minutes + r.adj_b_minutes
         = r.clocked_minutes AS identity_holds
FROM payroll.hours_run r WHERE r.pay_week_start = '2026-09-14';

-- lines must sum to the run
SELECT sum(rostered_minutes), sum(adj_a_minutes),
       sum(adj_b_minutes), sum(clocked_minutes)
FROM payroll.hours_line hl
JOIN payroll.hours_run r ON r.id = hl.run_id
WHERE r.pay_week_start = '2026-09-14';

-- the generated hours columns must agree with the minutes
SELECT staff_name, rostered_minutes, rostered_hours,
       round(rostered_minutes / 60.0, 2) AS expected_hours
FROM payroll.hours_line hl
JOIN payroll.hours_run r ON r.id = hl.run_id
WHERE r.pay_week_start = '2026-09-14'
  AND rostered_hours <> round(rostered_minutes / 60.0, 2);   -- expect 0 rows

-- every line should reach an employee through the bridge
SELECT hl.square_team_member_id, hl.staff_name, e.employee_code
FROM payroll.hours_line hl
JOIN payroll.hours_run r ON r.id = hl.run_id
LEFT JOIN payroll.employee e
       ON e.square_team_member_id = hl.square_team_member_id
WHERE r.pay_week_start = '2026-09-14' AND e.employee_code IS NULL;
```

The last one matters most. A line that does not reach an employee will appear in
`v_pay_variance` as `UNKNOWN IN SQUARE`, and a bridge gap is the failure mode
that once hid 407 hours.

## 6. The promotion aborted on `cafe.purchases.in_invoice_total` — cause and fix

```
psycopg2.errors.NotNullViolation: null value in column "in_invoice_total"
of relation "purchases" violates not-null constraint
```

**Nothing was written.** `run()` calls `conn.commit()` once, after the whole
loop, so the abort rolled the lot back: `cafe.invoices` 328 rows,
`cafe.purchases` 4027, none created on 29 September, and every staging row still
`verified`. The only trace is a burnt sequence value.

### Cause

`cafe.purchases.in_invoice_total` is `boolean NOT NULL DEFAULT true`. Five of the
44 verified `cafe_line` records carry `in_invoice_total: null` in their payload.
`build_row` copied that key through, so the INSERT named the column with an
explicit NULL — **and an explicit NULL overrides a default rather than falling
back to it.** The database would have filled the column itself had the INSERT
simply not mentioned it.

This is the same fault as migration 013 passing `filter = NULL` over
`nav_tab_source.filter`'s `DEFAULT '{}'::jsonb`. Second time in this build, from
the other direction: once in hand-written SQL, once in the promoter.

### Why the dry run said "no blocks found"

`required_columns()` selects NOT NULL columns **with no default**
(`d.adbin IS NULL`), which is right — a column with a default needs nothing from
the record. So `in_invoice_total` was never in the set the pre-check tests, and
the pre-check was not wrong to omit it. The gap was that `build_row` would then
go on to write a null into exactly such a column. The check and the writer
disagreed about what a default means.

`build_row` already filtered `extras` with `v is not None`. It did not filter the
payload. That asymmetry was the bug.

### Fix applied to `promote.py`

- new `defaulted_not_null(cur, schema, table)` — NOT NULL columns that *do* have
  a default, the mirror image of `required_columns`;
- `build_row(..., omit_if_none=())` drops any key whose value is None when the
  destination column is in that set, so the default applies;
- computed for parent and child at plan time, carried in the plan, and used by
  both the preview and the write, so the dry run and the real run build the same
  row — which is the property that failed here;
- the drop report now separates *no column in the destination* from *held in
  staging on purpose*, so `payload.notes` stops being reported as a loss.

The rule is deliberately narrow: only NOT NULL columns with a default. For those,
writing NULL is certain to fail, so omitting cannot break anything that works
today. A null for a nullable column is still written as NULL.

### Blast radius across all 13 record types

One column, and only one:

| Record type | Column | Staged rows carrying null | Staged rows with the key |
|---|---|---|---|
| `cafe_line` | `in_invoice_total` | 19 | 66 |

Nothing else in the registry can reach a NOT NULL-with-default column with a
null. The five affected verified rows:

| Supplier | Item | Line total |
|---|---|---|
| City of Adelaide | Outdoor Dining Permit Renewal | 612.00 |

### Positive evidence that `true` is right for all five

All seven verified invoices reconcile **exactly** ex-GST with every line counted
in, and each one's assessed GST equals its header GST:

|---|---|---|---|---|---|
| City of Adelaide | 612.00 | 612.00 | 0.00 | 0.00 | 0.00 |

was measuring the wrong thing, which is the failure mode this project keeps
meeting: checking a neighbour of the thing that can be wrong.

### The remaining producer question

The producer sets `in_invoice_total` on most lines and omitted it on the
23 September batch. Leaning on the default is safe for an ordinary line and
unsafe for a surcharge line, where the correct value is `false` and the default
would silently make it `true` — inflating the invoice total the reconciliation
is checking. The instruction block should require the field explicitly rather
than let it be absent.
