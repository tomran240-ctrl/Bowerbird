
The kws115 MCP connector is READ-ONLY. Every write goes as a .sql
script saved to the Database Project folder for Tom to run:
  psql kws115 -f <script>
Terminal is granted at tier "click" with no typing, so running psql
directly is not possible. Scripts are the only path.

DO NOT WRITE A LITERAL VERSION NUMBER INTO A rule_versions INSERT.
New in v5, defects D-2026-09-09-08 and D-2026-09-09-14. This is the
most important clause in this rule and it exists because the register
lost five rule bodies without reporting a single error.

  A version number written into a DRAFT is a claim on a key that only
  becomes real when the script RUNS. Two drafts can hold the same
  (rule_id, version) for a week. Both guard their insert
  WHERE NOT EXISTS (... rule_id = X AND version = N), so whichever
  runs second is SKIPPED IN SILENCE and its assertion - which asks
  only whether a current version with that number exists - PASSES.
  The run reports success while its change was thrown away.

  DERIVE IT:
    (SELECT coalesce(max(version), 0) + 1
     FROM normalisation.rule_versions WHERE rule_id = 'RULE-X')

  GUARD ON THE CHANGE, NOT THE NUMBER. Key the idempotency guard on
  an anchored change_reason prefix unique to this script, for example
  'SCRIPT 2026-09-10:', combined with rule_id.

  ASSERT THE BODY YOU MEANT LANDED. An assertion that some row with
  version N exists proves nothing. Assert that the row carrying THIS
  script's change_reason marker exists and is the one with
  superseded_at IS NULL.

  WHAT WAS LOST, so this cannot be dismissed as theoretical. On 2 Sep
  2026 six rule versions were drafted and never run. RULE-CS v2 and
  RULE-FN v4 were taken by other scripts on 7 and 8 Sep; RULE-DUP v3,
  RULE-GST v3 and RULE-SQL v4 were taken on 9 Sep. Five of the six.
  Only RULE-PA v2 survived, because no other script wanted the
  number.

  THE COMPARISON THAT CATCHES A COLLISION ALREADY DRAFTED is
  pre-flight point 8 below. It was stated here as prose in v5 and
  nothing ran it, which was itself logged as D-2026-09-10-01.

A SCRIPT IS EITHER A DRY RUN OR A COMMIT-ONLY SCRIPT. IT CANNOT BE
BOTH. New in v4, defect D-2026-09-09-08. v3 required BOTH "several
small separately-committed transactions" AND "swap ROLLBACK for COMMIT
and run the same file again". Those two are mutually exclusive, and
following both produced a "dry run" that committed three quarters of a
schema migration.

  (1) DRY RUN FORM. A SINGLE transaction ending in ROLLBACK. No
      intermediate COMMIT anywhere in the file. If the change is too
      large for one transaction, it is too large for the dry-run
      convention - use form 2.

  (2) COMMIT-ONLY FORM. Several separately-committed steps. It MUST
      say COMMIT-ONLY at the top, MUST be idempotent step by step
      (CREATE ... IF NOT EXISTS, DROP CONSTRAINT IF EXISTS, guarded
      ALTERs, NOT EXISTS inserts) so a partial failure is resumed by
      re-running, and MUST NOT carry a trailing ROLLBACK that implies
      a dry run it cannot deliver.

  WHERE APPLICATION CODE MUST CHANGE WITH THE SCHEMA, the code edit is
  prepared BEFORE the script is handed over and applied the moment the
  relevant step commits. Not deferred to "the commit run" - as the
  above shows, the commit may already have happened. On 9 Sep 2026 a
  table rename went live while invoicing_db.py still named the old
  table, so tenant electricity recovery would have raised "relation
  does not exist".

  A DELETE-THEN-RELOAD PAIR IS ONE OPERATION. Where step 1 destroys
  data and step 2 restores it, say so at the TOP of the script and
  again in a RAISE NOTICE at the end of the delete, because the
  failure mode when step 2 is skipped is SILENT - the reload's
  ON CONFLICT reports "skipped" exactly as it would for correct data.

ASSERTIONS MUST TEST WHAT THE SCRIPT DOES, NOT A CONVENTION.
New in v4. An assertion that is STRICTER than the change will roll
back correct work. A script that repointed 16 filenames asserted "no
source_file anywhere contains 'Amt'" - but 41 rows contained it and
only 16 were wrong; the other 25 were a legitimate older naming
generation. All 16 correct updates were destroyed to enforce a rule
nobody had agreed.

  Assert the rows the script wrote, by business key, and nothing
  wider.

AN ASSERTION MUST DISTINGUISH "MY PRECONDITION IS ABSENT" FROM
"I FAILED". New in v4, defect D-2026-09-09-05. Where a step depends on
an earlier commit or an external load, check the precondition FIRST
and RAISE NOTICE "skipped, and this is expected" rather than
EXCEPTION. An assertion that reports the same hard failure for a
missing precondition as for a real fault converts an ordering mistake
into what looks like data loss.

A PREDICTED FIGURE PRINTED INSIDE A SCRIPT IS DERIVED, NOT TYPED.
Restored in v5. Where a step forecasts a count, state the arithmetic
that produces it, so a slip is visible at the point it is made. On
26 Aug 2026 a step forecast "11 of 26" where the answer was 11 of 27,
because the four versions the script itself added were left out of the
denominator, and the file would otherwise have stood as a permanent
record of a number that was never right.

PRE-FLIGHT BEFORE HANDING OVER ANY .sql - all nine, mechanically:
  1. For EVERY RELATION THE SCRIPT TOUCHES, including views and
     including read-only verification steps, one schema query, ALL SIX
     columns:
       SELECT column_name, data_type, is_nullable, column_default,
              is_generated, is_identity
       FROM information_schema.columns WHERE ...
     Then supply every is_nullable='NO' with a NULL default; OMIT
     every is_generated='ALWAYS'; omit is_identity='YES'.
     VIEWS ARE THE SHARP EDGE: a view column can differ in TYPE from
     the base column of the same name.
  2. grep for backslash meta-commands at line start, expects zero
     hits. Also grep non-ASCII.
  3. Confirm no double-hyphen comments.
  4. Parse-check with pglast, BOTH the file text and
     ' '.join(text.split()). Both must return the same statement count.
  5. For every relation touched, run
       SELECT conname, pg_get_constraintdef(oid)
       FROM pg_constraint WHERE conrelid = '<schema>.<table>'::regclass;
     and confirm every literal the script writes into a constrained
     column appears in that column's allowed list. Note every UNIQUE
     constraint and confirm each idempotency guard keys on one.
     Promoted from habit to rule in v4 - it was logged as
     D-2026-09-08-09 and applied to six scripts before being written
     down, which is exactly the drift the register exists to prevent.
     PG_CONSTRAINT CANNOT SEE AN INDEX. New in v7, defect
     D-2026-09-14-01 (live-session). Also run

       SELECT indexname, indexdef FROM pg_indexes
       WHERE schemaname = '<schema>' AND tablename = '<table>';

     Any UNIQUE index, and especially a PARTIAL one carrying a WHERE
     clause, constrains what may exist MID-TRANSACTION and therefore
     dictates statement ORDER. It is enforced per statement, never
     deferred to commit. pg_constraint does not list it, and Postgres
     calls it a "unique constraint" in the error text when it fires,
     so a reader who has just run the pg_constraint query and seen
     six rows will reasonably conclude the query was mis-run rather
     than that the check has a blind spot.

     normalisation.rule_versions carries exactly such an index,
     rule_versions_one_current, UNIQUE (rule_id) WHERE superseded_at
     IS NULL. It forces the parent to be stamped superseded BEFORE
     the successor is inserted. Every rule-version script written
     before 14 Sep 2026 happened to get that order right, so nothing
     recorded that the order was load-bearing rather than stylistic
     until a dry run failed on it.

     AND ASK pg_trigger IN THE SAME BREATH. Triggers force write
     order for the same reason and are already known to do so here:
     job_completion_guard cost two failed runs on 8 Sep 2026 purely
     on ordering.

       SELECT tgname, pg_get_triggerdef(oid) FROM pg_trigger
       WHERE tgrelid = '<schema>.<table>'::regclass AND NOT tgisinternal;

     EACH CATALOGUE IS BLIND TO THE NEXT, and that is the general
     lesson rather than a fact about two of them.
     information_schema.columns cannot see a value-list CHECK, which
     is why point 5 queries pg_constraint at all. pg_constraint
     cannot see an index. An index cannot see a trigger. A pre-flight
     that stops at whichever catalogue the last defect named will be
     blind in exactly the next place.

  6. EXECUTE every read-only verification statement through the kws115
     read connector before handing the script over. Restored in v5.
     It is free, the connector is read-only so it cannot do harm, and
     it catches exactly the class the other five cannot: a column that
     does not exist, a wrong type, a function signature that does not
     match.
  7. WHERE THE SCRIPT CONTAINS A DO BLOCK, intersect the names
     DECLAREd in it against every table alias used inside it. The
     intersection must be EMPTY. New in v6, defect D-2026-09-10-02.

     PL/pgSQL resolves a qualified reference to the VARIABLE, not the
     table, and raises "column reference x.y is ambiguous" only at
     RUN time. On 10 Sep 2026 a DO block declared a record variable r
     for its loop and, forty lines later, aliased
     normalisation.rules AS r. The assertion aborted the transaction
     it was meant to certify.

     POINTS 4 AND 6 ARE BLIND TO THIS, which is why it needs its own
     point rather than a sentence somewhere. pglast parsed the file
     to the same statement count before and after the fix, because a
     DO block body is a string literal to the parser. The offending
     query was ALSO executed through the read connector during
     pre-flight and returned the right answer, because standing alone
     it is unambiguous - the fault is an interaction between a
     statement and its enclosing block, and every other point tests
     statements in isolation.

     CONVENTION THAT REMOVES THE NEED TO CHECK: prefix every DECLAREd
     variable with v_ or n_. A table alias never carries that prefix,
     so the collision cannot arise. The check stays mandatory anyway,
     because a convention is not a control.

  8. FOR EVERY SCRIPT THAT WRITES RULE VERSIONS, compare every
     (rule_id, version) pair it inserts against v_rules_current AND
     against every other .sql in the Database Project folder that has
     not been confirmed run. Promoted from prose to a mechanical
     point in v6, defect D-2026-09-10-01, because as a clause in the
     body above it had no runner and nothing performed it.

     A script that derives its versions writes no literal pair and so
     has nothing to compare, which is the intended state. The scan
     exists for the scripts already sitting in the folder, drafted
     under an older rule.

       grep -oE "'RULE-[A-Z0-9]+',[[:space:]]*[0-9]+" over the folder
       gives the pairs. Any pair whose version is already current, or
       which appears in two files, is a collision.

     WHAT TO COUNT, AND OVER WHICH FOLDERS. New in v8, defects
     D-2026-09-16-01 (weekly-workflow-defect-review) and
     D-2026-09-22-02 (weekly-workflow-defect-review).

     THE UNIT IS THE DISTINCT (rule_id, version, file) TRIPLE. The
     grep returns raw occurrences, and a pair written twice in one
     file, once in its INSERT and again in the script's own
     assertion block, is ONE claim on ONE key and not two. Three
     consecutive runs reported three different counts from a folder
     that had not changed, because the unit was never stated.
     Report the distinct triple count AND the file count, and say
     which is which.

     THE SCAN COVERS EVERY FOLDER FROM WHICH SCRIPTS ARE RUN AGAINST
     kws115. It is not one named folder, and this rule deliberately
     names none: a path written into a rule body is a copy of
     something that can move and cannot learn that it did, which is
     the same fault as an enumerated constraint value further down.

     THE COST OF HAVING NAMED ONE. On 23 September 2026 a second
     population of migration scripts was found under an application's
     own db directory, and it had written rule versions the day before. Neither the register scan nor the cited-id
     check had ever looked at them, because both were scoped to the
     one folder this rule used to name, and the migration scripts
     ran their own copy of the scan scoped to THEIR folder. Each
     population was checking itself and neither was checking the
     other, so a collision between them would have been invisible to
     both. Enumerate the folders at scan time.
     WHEN A COMMENT MUST NAME A COLLIDING PAIR, NAME THE FILE AND THE
     RULE, NEVER THE PAIR IN THE GREP FORM. New in v7, defect
     D-2026-09-14-02 (live-session). This scan is a textual grep over
     the folder. It does not parse SQL and cannot tell a block
     comment from an INSERT, so a pre-flight note quoting a pair
     verbatim makes its own file report as carrying a literal pair on
     every future scan - in a file whose whole design is that it
     derives its version and writes no literal at all. A control that
     its own documentation can trip produces a false positive in a
     scheduled task's output days later, pointing at a file that is
     correct.


     A DRAFTED SCRIPT HAS NO RUN-STATUS FIELD anywhere in this
     system, so "not confirmed run" is established from the defect
     logs and from the register, not from the file. That is the
     residual weakness of this point and it is stated here rather
     than left to be rediscovered.

  9. EVERY DEFECT ID LITERAL IN THIS SCRIPT MUST NAME ITS TASK,
     AND MUST RESOLVE TO A BLOCK THAT EXISTS. New in v7, defect
     D-2026-09-10-03 (weekly-workflow-defect-review) and
     D-2026-09-14-01 (weekly-workflow-defect-review).

       grep -oE "D-[0-9]{4}-[0-9]{2}-[0-9]{2}-[0-9]{2}" over the file

     QUALIFICATION. For every id the grep returns, the text that
     follows it must be a parenthesised task stem:
     (weekly-inbox-filing-review), (weekly-workflow-defect-review),
     (weekly-filing-completion), (live-session), and so on. A bare id
     fails, everywhere in the file alike: header comment, block
     comment, rule body text, and the defect_ref literal.

     NORMALISE WHITESPACE BEFORE MATCHING, exactly as point 4 does
     for the parse check. A comment that wraps between the id and its
     qualifier is correctly qualified to a reader and reads as bare
     to a line-oriented grep. This script itself produced three such
     false positives on its own first pass, which is how the clause
     came to be here.

     THE EVIDENCE EXEMPTION, stated so it is not abused. An id quoted
     as a STRING FOUND IN ANOTHER FILE, in order to report that it
     was written badly, is not a citation and does not have to carry
     a qualifier it never had. Say so at the point of quoting. An id
     given as the REASON for a change is a citation and always
     carries its task.

     RESOLUTION. Each id must also appear as a block in
     Knowledge Base/115KWS/defects/YYYY-MM-DD-<task>-defects.txt for
     the task it names. A qualified id that names no block is the
     same fault one step further on.

     RULE-DEF v1 ALREADY REQUIRES THE QUALIFICATION HALF. This point
     exists because requiring it settled nothing. The clause was
     breached on the day RULE-DEF committed, and again four times on
     14 Sep 2026: three bare ids went into the RULE-FN v7 body and
     are now permanent text in the register, and two scripts of the
     same morning cited an id that no log holds. The ids concerned
     were, as literals found in those files and quoted here as
     evidence rather than cited as reasons, D-2026-09-08-06,
     D-2026-09-02-01, D-2026-08-24-01 and D-2026-09-10-13.

     A defect_ref IS THE EXPENSIVE ONE. A citation in a comment is
     read in context by whoever opens the file. A defect_ref column
     is read by query, out of context, and correcting it after the
     row commits needs a decision nobody has made. Four rows have
     carried prose in that column since 02 September for exactly that
     reason.

     EVERY OTHER PRE-FLIGHT POINT IS BLIND TO THIS. They test
     schemas, constraints, parse trees, DO block scoping and rule
     version numbers. A defect id is none of those, which is why this
     needs its own point rather than a sentence elsewhere.

     THE RESOLUTION HALF CANNOT BE RUN FROM INSIDE psql. It reads the
     defects folder, not the database. It belongs to the pre-flight
     rather than to an assertion for that reason, and it is the one
     point on this list that a script cannot check about itself.

  A VIEW IS NOT A TABLE. Restored in v5. It does not inherit the
  column set or the column types of the objects it selects from. On
  26 Aug 2026 a verification statement over
  normalisation.v_rules_current failed with "function to_char(text,
  unknown) does not exist" - the view renders effective_from as TEXT
  because it applies to_char internally - and the same statement also
  selected defect_ref, which the view does not expose at all. TWO
  faults in one statement, the second queued behind the first, and it
  had passed all four of the then-current pre-flight points.

  WHERE A VIEW HAS ALREADY APPLIED to_char, DO NOT APPLY IT AGAIN.
  RULE-DT's instruction to render dates with to_char is correct for a
  raw date column and WRONG for a column that is already text. This
  sentence is the resolution of that conflict and is the reason it is
  stated here rather than left for a later run to rediscover.

  A COLUMN WITH NO CHECK IS NOT A FREE-TEXT COLUMN. New in v4, defect
  D-2026-09-09-03. Before writing a literal into an unconstrained text
  column, run
    SELECT <col>, count(*) FROM <table> GROUP BY 1 ORDER BY 2 DESC
  and confirm the value already appears, or state why a new one is
  being introduced. accounting.invoices.status has no CHECK and holds
  only 'auto' and 'reviewed'; a proposed 'Paid' would have been
  accepted by the database and meant nothing.

SCRIPT FORM - not negotiable:
  - Plain ASCII. No non-ASCII characters at all.
  - NO psql backslash meta-commands. None. Use
    SELECT 'STEP 1.1 ...' AS check; for section headers.
  - Block comments only, never the double-hyphen form.
  - A count printed after each step.
  - An assertion DO block for anything the script cannot set directly.
  - NO IMPLICIT STRING CONCATENATION. Adjacent quoted literals on
    successive lines are valid SQL, read well at the ASCII column
    width these scripts keep to, and become a SYNTAX ERROR the moment
    the newlines collapse. That is the hazard point 4 detects and the
    hazard the -f instruction avoids, so a script relying on it works
    one way and fails the other. Write a long literal as ONE long
    line, or dollar quote it. New in v8, defect D-2026-09-16-03
    (weekly-workflow-defect-review).

VERIFY MARKERS - BUSINESS KEYS, NEVER IDS. Ids move. On 5 Aug 2026
jobs 150 and 170 were legitimately merged into JOB-0143 and JOB-0022,
with the quotes repointed and an audit note recorded. On 19 Aug 2026
the two id-based markers reported those rows missing: a false alarm
indistinguishable from real data loss, which cost a full
re-investigation to clear. That narrative is restored in v5 because
the instruction without it reads as a style preference. Use
job_number, quote_number, tech_report, source_file, document_ref,
invoice_number, payment_number, or a natural key such as
(nmi, bill_period_start, bill_period_end).

BEFORE DELETING A PARENT ROW, ask pg_constraint which tables reference
it. Do not hand-list them. Twelve tables carry an FK to
maintenance.jobs; three are ON DELETE CASCADE and vanish silently
rather than blocking. Note pg_constraint does NOT expose NOT NULL.

Sequences are non-transactional and a failed transaction still burns
values. Do not promise specific id numbers in a pre-run summary;
describe rows by their business key.

ASSERTION SCOPE. An assertion DO block must test ONLY rows written by
the transaction it sits in. An assertion that counts rows written by a
sibling step ALWAYS misreports under ROLLBACK and ALWAYS passes under
COMMIT, so the flaw never surfaces through normal use. On 24 Aug 2026
this shape appeared three times in one day; the third was a genuine
mistake and reported "STEP 3 FAILED: expected 2 rows, found 1" when
STEP 3 was entirely correct.

Put any cross-step check in a FINAL READ-ONLY STEP that runs after the
others have committed, so it cannot abort the step it reports on.
Where a step legitimately depends on an earlier step's commit, say so
in the step header, so its dry-run failure reads as expected rather
than alarming.

GUARD KEYS. A NOT EXISTS or ON CONFLICT idempotency guard must key on
a value unique to the ONE row being inserted - a business key, or an
anchored prefix where no business key exists. FREE TEXT IS NEVER A
SAFE GUARD KEY.

Descriptions in this database deliberately cross-reference each other,
which is a virtue in the prose and a hazard in a WHERE clause. On
24 Aug 2026 a guard keyed on free text inside defect_description
suppressed its own INSERT, because the sibling row inserted moments
earlier enumerated the same items and contained the phrase being
matched. Two defects were meant to be raised and one was, while the
run summary said both. Rule bodies quote other rules by name for the
same reason, so a guard matching a rule name inside body text will
match rows never intended. Key a rule_versions guard on
(rule_id, version) where the version is known, on
(rule_id, anchored change_reason prefix) where it is derived, and a
rule_consumers guard on (rule_id, task_id). Restored and extended in
v5.

Where an anchored prefix is the only available key, test every prefix
against every other candidate row in the same script for uniqueness
BEFORE the COMMIT swap. Restored in v5.

A FIGURE WRITTEN INTO PERSISTENT TEXT. New in v8, defect
D-2026-09-17-03 (weekly-workflow-defect-review).

The PREDICTED FIGURE clause above governs a figure a script PRINTS.
It does not reach a figure a script WRITES into a rule body, a
change_reason or a defect_ref, and that is the worse case.

A SCRIPT'S FIGURE IS CHECKED WHEN THE SCRIPT RUNS and the file is
then spent. A FIGURE IN A RULE BODY IS COMMITTED TEXT: read for as
long as that version is current, testable by no assertion after
commit, and correctable only by a supersession. Rows in this register
already carry prose in a column nobody has decided how to correct.

WHERE A SCRIPT WRITES A FIGURE INTO PERSISTENT TEXT, THE SAME TEXT
CARRIES THE QUERY THAT PRODUCES IT, so a later reader re-derives it
rather than trusting it. A body naming a count of columns and nothing else is unsafe. RULE-FN
v9 already models the compliant form for that very figure: it carries
the catalogue query, the count that query returned, and the date it
was run, so a reader re-derives instead of trusting. Follow it.

THIS CLAUSE'S OWN SIBLING SCRIPT WAS DRAFTED WITH THE FAULT IN IT.
The RULE-DEF v2 script of 23 September 2026 asserted "expected 25"
current versions. RULE-FRM was created at 08:40 that morning and the
answer was 26. Pre-flight point 6 caught it before hand-over and the
step was rewritten to compare two derived counts. A typed figure
goes stale on the timescale of hours, not months.

A RULE BODY THAT ENUMERATES THE SCHEMA. New in v8, defects
D-2026-09-17-02 (weekly-workflow-defect-review) and D-2026-09-21-04
(weekly-inbox-filing-review).

TWO SHAPES OF ONE FAULT, stated together because the fix is the same.
A rule body that enumerates part of the schema has made a copy, and
the copy cannot learn that the original changed.

  A LIST OF DATABASE OBJECTS. A rule required a search of seven named
  columns before renaming a file. All seven exist and all seven were
  verified, which is what the instruction about verifying absence
  asks for. There are twenty-seven such columns. A run that searched
  the seven and found nothing would have reported a file safe to
  rename, in the same confident form a complete check uses, having
  inspected a quarter of the places a reference can live. Verifying
  that every item on a list is real is NOT verifying that the list is
  complete, and a partial list is the more dangerous shape because
  every item in it checks out.

  A CONSTRAINT'S PERMITTED VALUES. A rule stated that a status
  constraint "permits only those three values". It permits four.

EITHER DERIVE THE LIST FROM A CATALOGUE QUERY WRITTEN INTO THE BODY,
OR STATE THE TOTAL THE LIST IS DRAWN FROM. Never enumerate a
constraint's allowed values at all: name the constraint and require
the reader to query pg_constraint, which pre-flight point 5 already
makes mandatory for every script.

WHY THIS SITS BESIDE POINT 5 AND NOT IN THE RULE THAT WAS STALE.
Point 5 exists because a rule cannot be trusted about a constraint.
This is that same proposition applied to rule bodies generally, so it
reaches every task. Placed in the rule that happened to be wrong it
would have reached that rule's two consumers.

A SWEEP OF THE WHOLE REGISTER on 21 September 2026 found the class to
be real but rare. The sweep is cheap and repeatable: re-derive its
result rather than quoting this sentence. The count is deliberately
not restated here, because a clause about figures that go stale must
not plant one.

HOW SOON IS TOO SOON TO SUPERSEDE. New in v8, defect D-2026-09-18-02
(weekly-workflow-defect-review).

DO NOT SUPERSEDE THE SAME RULE TWICE IN ONE DAY. Where a further
small clause arrives for a rule already superseded today, QUEUE it,
and say in that run's log that it is queued and what it sits behind.

ONE CONVENTION, NOT TWO. The practice had drifted into "not twice in
a week" for one rule and "not twice in a day" for another, each
inferred by a run reading the previous run's prose rather than
fetched. A DAY IS THE RULE. Tom settled it on 23 September 2026.

IT IS A FLOOR, NOT A DELAY. A clause correcting a statement VERIFIED
FALSE BY QUERY is not small and is not queued. The convention exists
so that several small clauses travel together and arrive as one well
argued version, not so that a known fault waits for company.

SAY WHAT IS IN THE QUEUE, EVERY RUN. A queue that lives only in one
run's prose is the drift this clause exists to stop. The queue behind
this rule grew over several days before it was drained, and the only
reason each run knew the queue existed at all was that the previous
run had happened to write it down.
